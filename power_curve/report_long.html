解读

区间行为说明
150→300W主升段(合计 3.27×)decode 速度几乎与频率成正比(18.5→60.5 t/s ≈ 634→1386 MHz),说明这段瓶颈就是功率墙压着的 SM 频率。每 50W 平均换 40%+ 速度,能效最好的区间。
300→450W次升段(+15%)频率继续爬(1386→2600 MHz)但速度曲线开始弯——KV 搬运的带宽消耗占比上升,频率红利被稀释。
450→600W平台(+0.5%)频率到顶(2777 MHz,Vmax),速度完全不再响应功耗。600W 与 450W 的差距在测量噪声内。
为什么长上下文比短负载慢一半? 每 decode token 除了搬 16GB 权重,还要读/写当前上下文的全部 KV cache。 3K token × q8_0 K+V(每层 ~64B/token)× 64 层 ≈ 120MB 额外带宽流量/token,叠在 16GB 上,decode 时间常数直接拉长。 实际聊天上下文常到 10–30K token,真实体感速度会更低——这也是为什么"峰值 t/s"容易给人虚假的信心。
频率曲线的用法: 想不降太多性能就省电,把上限设在你需要的"工作频率"上—— 比如只要 2 GHz 级别(短负载 ~55W 以下即可,长上下文 ~350W 档)就完全够用; 反过来,上限设 550W 以上没有任何意义,因为 Vmax 在 500W 附近就到了。

方法与数据

脚本 D:\AI\llm-monitor\power_curve\:bench_power.py(固定 ~3.1K-token prompt + 1024-token 输出; 速度读 server tokens_predicted 计数器;3Hz 采样 power.draw + clocks.sm; 每次 run 前等待 server 空闲,忙则跳过)。sweep.ps1 提权逐档 nvidia-smi -pl 并读回确认,结束自动恢复 300W。 原始数据:results_150_600.jsonl(30 run,0 跳过)。 已知干扰:被测模型即当前会话服务模型,若测量期间有人(包括 agent 自己)在聊天会污染该档—— 本轮全程 30/30 干净(空闲闸门生效);400W run0 的 9.1 t/s 为 warmup 离群,中位数未受其影响。
